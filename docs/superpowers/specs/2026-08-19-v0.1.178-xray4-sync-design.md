# v0.1.178-xray4 官方同步设计

日期：2026-08-19
状态：用户已批准，beta1 实施中
目标候选：`0.1.178-xray4-beta1` -> `0.1.178-xray4-beta2`
目标正式版：`0.1.178-xray4`

## 1. 目标与范围

本轮将当前 Xray 正式版 `v0.1.177-xray4` 同步到官方 `v0.1.178` 及其对应的最新 `origin/main`，并继续保留 Xray 的用户私有资源、代理订阅、Xray/sing-box 运行时、独立 GHCR 与更新链路。

固定同步点：

- 当前 Xray 基线：`d99115e760d5da85ffe5516f4ef67e98ad5ee3a7`
- 官方 `v0.1.178`：`e0c48a19ed794a565e3858662520afe0a1f9f0ba`
- 官方最新 `main`：`ae62854abcb1285e0abc4e69d7465e78518d7d4b`

官方 Tag 后的 39 个提交也纳入本轮。除渠道监控配额模式修复、国产供应商账号测试路由、OpenAI 容量恢复、版本同步和文档修复外，还包括 Responses 到 Chat 的 reasoning 内容回传与缓存、Responses 输入 token 预检、Composite Codex 端点、Composite 对国产供应商的支持、Chat 非流式故障转移、WS bridge 工具保留以及 Grok 4.6 xhigh 推理档位保留。

官方 `v0.1.178` Tag 所指文件树中的 `backend/cmd/server/VERSION` 仍为 `0.1.177`，Tag 后提交 `49504adc9` 才同步为 `0.1.178`。因此本轮必须合并上述最新 `main`，不能只停在 Tag。

## 2. 已确认的行为决策

1. beta1 仅向管理员开放 Kimi、智谱、DeepSeek；普通用户仍保持原有平台范围。
2. beta1 完整验收无阻断后，beta2 再为普通用户私有账号和私有分组适配 Kimi、智谱、DeepSeek。
3. 采用官方随机 Codex 指纹 seed。已启用 `device`、`session`、`full` 的存量账号升级后允许发生一次指纹变化；`off` 透传不受影响。
4. 全局渠道监控只能关联系统账号，不得读取普通用户的私有账号。
5. 每轮 GitHub 更新只允许一个最终打包提交，同时必须保留官方同步祖先关系。
6. Release 的 VERSION 校验必须在任何 Release 或 GHCR 产物生成前完成，且校验过程不得修改仓库或创建提交。

## 3. 提交拓扑

最终提交必须是唯一的双父合并提交：

```text
d99115e76  v0.1.177-xray4
    \
     M  v0.1.178-xray4 唯一项目提交
    /
ae62854ab  官方最新 main
```

- `M` 的第一父提交固定为 `d99115e76`。
- `M` 的第二父提交固定为 `ae62854ab`。
- beta1、beta2、测试修复和 Release 修改都通过 `git commit --amend` 更新 `M`，不新增 first-parent 提交。
- 候选分支、设计分支、中间提交和临时 Tag 不得推送到 GitHub。
- 正式 Tag 只能指向最终的 `M`。
- 创建 beta1 合并提交前必须确认 `MERGE_HEAD` 已更新为 `ae62854ab`，不能只把新官方文件复制进旧的 `82f7dd14f` 合并关系。
- 发布前必须验证上一公开 `xray/main..HEAD` 的 first-parent 路径只有一个项目提交，并确认第二父提交仍为官方同步点。

本设计文档的审核提交只保留在本地设计分支。实施时仅将文件内容纳入 `M`，不得 merge 或 cherry-pick 设计分支提交。

## 4. beta1 实施范围

### 4.1 官方功能同步

纳入官方 `v0.1.178` 与最新 `main` 的功能和修复，包括：

- Kimi、智谱、DeepSeek 管理员账号、分组、渠道定价、余额与配额能力。
- 渠道监控的探活、配额、探活加配额三种模式。
- 渠道模型分时倍率定价。
- OpenAI Team 联动熔断和账号批量设置。
- OpenAI/Codex、WS、工具协议、容量恢复和模型发现修复。
- Responses 输入 token 预检及 reasoning 内容在兼容桥接中的回传与缓存。
- Composite Codex 端点及 Composite 对 Grok、Kimi、智谱、DeepSeek 的完整路由支持。
- Grok、Ollama、Gemini、Antigravity、Ops、暗色模式和 i18n 修复。

### 4.2 Xray 能力保留

以下能力不得被官方版本覆盖或删除：

- 用户私有账号、分组、代理、兑换码和订阅资源所有权。
- 管理员、系统资源、公开代理和用户私有资源之间的访问矩阵。
- Xray 分享链接、机场订阅、Clash/Sing-box 导入和代理运行时生命周期。
- 用户私有 Base URL 的内网、环回、DNS 重绑定和重定向保护。
- Xray Core 与 sing-box 内置运行时。
- Xray 仓库地址、品牌、安装脚本、GHCR 镜像和独立更新链路。
- Xray 弹窗高度、内部滚动、用户资源页面和代理管理 UI。

### 4.3 beta1 平台边界

- 管理员账号、分组、筛选器、渠道和 Composite 功能完整显示已支持平台。
- 普通用户创建和编辑账号时隐藏 Kimi、智谱、DeepSeek。
- 普通用户现有 5 平台功能和 `/api/v1/my/*` 路由保持不变。
- 不得出现“用户看得到国产供应商但后端拒绝”的半完成状态。

### 4.4 Codex 指纹

官方随机 seed 逻辑必须覆盖管理员和用户私有 OpenAI OAuth 账号：

- 外部请求不得指定或伪造 seed。
- 首次启用收敛时生成 seed。
- 后续编辑、导入、复制和批量更新稳定保留同一账号 seed。
- 不同账号不得复用 seed。
- `off` 模式继续透传客户端原始标识。
- 迁移回填后必须验证存量账号的一次性轮换行为。

### 4.5 渠道监控隔离

- 配额模式创建、编辑和运行时都必须验证关联账号为系统账号，即 `owner_user_id IS NULL`。
- 前端远程账号搜索只能返回系统账号。
- 后端保存校验是最终权限边界，不能只依赖前端过滤。
- 删除系统账号后保持官方 `ON DELETE SET NULL` 行为。

## 5. beta2 用户端适配

beta1 完整验收无阻断后，将同一候选提交 amend 为 `0.1.178-xray4-beta2`，再实施：

- 普通用户私有账号支持 Kimi、智谱、DeepSeek。
- 普通用户私有分组支持三家国产供应商。
- 补齐用户端平台校验、协议、Base URL 预设、凭据构造和模型同步。
- 补齐账号测试、余额/配额显示、筛选器、导入、导出、复制和批量操作。
- 用户只能访问自己的账号、分组与代理；公共代理只开放使用权，不返回凭据。
- 全部用户操作继续使用 `/api/v1/my/*`，共享组件不得调用管理员 API。
- beta2 不放宽渠道监控只能读取系统账号的限制。

## 8. 网关与安全边界

- 所有使用用户私有账号发出的 HTTP 与 WebSocket 请求必须在 socket 层限制为公网目标；仅对该账号实际绑定的 Xray 本地监听地址开放精确例外，系统账号保持原行为。
- 官方新增的 Responses、Chat Completions、Messages、Anthropic native、WS/HTTP bridge、client tools 和 Composite 路径必须继续经过同一出站网络保护。
- OpenAI Team 402 联动仅允许影响相同 `OwnerUserID` 的 OAuth 账号；进程内去重键包含 owner，日志只记录 Team ID 哈希，不输出原始标识。
- 系统调度继续排除用户私有账号；账号、分组、代理继续按相同 owner scope 关联。
- 管理员系统账号不得错误绑定用户私有代理，普通用户不得读取其他用户资源。
- Composite 解析后的 Grok 与国产供应商目标必须遵循平台调度、计费、模型发现和权限约束。
- 官方完整功能优先采用官方实现；与 Xray 权限、安全或运行时边界冲突时停止实施并请求人工确认。

## 9. 前端合并原则

- 分组页同时保留所有者筛选、所有者列、平台入口、Composite 平台和 `time_pricing`。

## 10. 版本与 Release 流程

### 10.1 候选阶段

- `backend/cmd/server/VERSION` 使用 `0.1.178-xray4-beta1`，测试服务器显示同一 beta 版本。
- 三语 README 继续把 `v0.1.177-xray4` 标记为当前正式版，不得提前链接尚不存在的 178 Release。
- beta1 验收通过并进入用户端适配时，使用 amend 将 VERSION 更新为 `0.1.178-xray4-beta2`。
- beta 完整测试和服务器浏览器验收前，不创建 `docs/releases/v0.1.178-xray4_CN.md`，也不创建项目正式发布前备份。

### 10.2 发布工作流

`.github/workflows/release.yml` 必须执行发布前只读门禁：

- Checkout 本次 Tag，而不是默认分支，并确认该 ref 是真实 Git Tag 且指向当前 `HEAD`。
- Tag 去掉 `v` 前缀后必须与仓库 VERSION 完全一致。
- 不一致时在前端发布构建、GoReleaser、GitHub Release 和 GHCR 之前失败。
- 校验任务仅授予 `contents: read`。
- 手工 Tag 输入、Tag 正文和仓库元数据只能通过步骤环境变量传给 shell，不得直接插值进 `run`；多行输出使用不可预测的分隔符。
- 永远不修改 VERSION、不上传改写后的 VERSION artifact、不创建提交、不执行 `git push`。

### 10.3 正式发布顺序

1. beta1 和 beta2 依次完成服务器与浏览器验收。
2. 根据真实增量创建 Release 审核稿并交用户审核。
3. 根据用户意见修改，直到用户明确审核通过。
4. 用户明确下达“上传”指令后，创建并校验一次标准正式发布前项目备份。
5. 将 beta2 改为正式版本，并把三语 README 更新到 `v0.1.178-xray4`。
6. 最后 amend 唯一双父提交，复核文件树、父提交、VERSION 和 Release 文案。
7. 推送唯一提交到 `xray/main`，等待分支 CI 与安全扫描全部成功。
8. 创建并推送指向该提交的正式 Tag。
9. 核对 GitHub Release、安装包、checksums、多架构 GHCR、版本接口和更新链接。

禁止使用 `SIMPLE_RELEASE=true` 发布正式版。

## 11. 测试与服务器验收

每个 beta 都必须完成：

- 前端完整测试、类型检查、Lint 和生产构建。
- 后端 unit、integration 和 golangci-lint。
- 在 UTC 环境重复验证 `TestGroupUsageRollupTriggerKeepsWatermarkForTodayInsert`。

- 候选 Docker 镜像中的 VERSION、Xray、sing-box 和更新链路检查。

内置浏览器黑盒验收覆盖桌面 `1280x720`、移动端 `390x844`、明暗主题：

## 12. 异常处理

- 自动合并结果不得按整文件接受一侧；所有语义冲突按本设计逐项组合。
- 构建或测试失败时停留在当前 beta，通过 amend 修复并重新执行对应完整验证。
- 官方行为与 Xray 权限、资源所有权、安全或 UI 发生未定义冲突时，明确报告并等待用户决定。
